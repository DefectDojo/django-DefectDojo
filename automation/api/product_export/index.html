Product export

What it is#

DefectDojo has two API endpoints that export data:

  • GET /api/v2/export/manifest/ describes the instance: its product types and products with their counts, the reference data, and the users.
  • GET /api/v2/export/products/{id}/ streams one product with its engagements, tests, findings, notes, files and risk acceptances.

Use them to back up a product, move it to another instance, or keep a mirror.

Only a superuser can call these endpoints. Any other caller gets a 403. Authenticate with an API v2 key in the Authorization: Token header, as for every other API v2 endpoint.

Because the caller is always a superuser, the export does not filter by permissions. Private notes cross. A product id that does not exist gets a 404.

Before you export#

The export does not take a snapshot of the database. If a user changes the product during the stream, the change can show in one line and not in another. If the instance has a read-only mode (DefectDojo 3.4.300 or later), turn it on first so the export is consistent.

The manifest: GET /api/v2/export/manifest/#

The response is one JSON object with these keys:

KeyWhat it holds
schemaThe version of the export format. It is 1.
generated_atThe time the server built the response, in ISO 8601.
sourceThe instance: version, install_id, url and locations_enabled. install_id is a random id for the instance.
max_file_bytesThe file cap that the files_over_cap counts use.
tokenThe caller: username, is_superuser and expires_at. expires_at is null when the API key does not expire, and always null under session or basic authentication.
scan_typesThe scan types of every test on the instance, sorted.
referenceThe lookup tables that the product export refers to by id: sla_configurations, development_environments, regulations, test_types, note_types, product_platforms, product_lifecycles, product_origins and users. Each user carries its contact_info. The product carries its platform, lifecycle and origin as the value of an entry in these tables.
product_typesOne entry per product type, with id, name and counts. Its counts also hold products.
productsOne entry per product, with id, name, prod_type (the product type id) and counts. It holds description, tags (a list of names), business_criticality, sla_configuration (an SLA id) and three user ids: product_manager, technical_contact, team_manager. Each value is the one /api/v2/products/ returns, and it is null where that endpoint returns null.
totalsThe counts of all products added together, plus product_types and products.

install_id stays the same for the life of the instance, with one exception. The initializer reloads the settings fixture when first boot runs again, and that load writes a new install_id. First boot runs again only when the DD_ADMIN_USER account does not exist. That re-initialization also resets every other system setting.

The manifest takes one parameter:

ParameterTypeDefaultWhat it does
max_file_bytesinteger, 0 or more10485760 (10 MiB)The file cap. A file larger than this counts in files_over_cap.

An empty value, as in ?max_file_bytes=, uses the default. Any other value that is not a whole number of 0 or more gets a 400. To count files_over_cap, the server reads the size of every file in storage. On an instance with many files, the manifest can take some time.

The product stream: GET /api/v2/export/products/{id}/#

The response has the content type application/x-ndjson: one JSON object on each line. The Content-Disposition header names the file defectdojo-product-2-export.ndjson. The endpoint takes the same max_file_bytes parameter as the manifest.

The lines come in this order:

  1. One header line.
  2. Every engagement of the product, by id.
  3. Every test, by id.
  4. Every finding, by test and then by id within the test. You can group a test’s findings as they arrive.
  5. Every risk_acceptance, by id.
  6. One end line.

Each object has its own line and names its parent by id. Notes, files, endpoint entries and finding groups nest in their line. A stream that has no end line is incomplete. The connection dropped before the export finished, so export the product again.

A line can be many MiB. One 10 MiB file makes a line of about 13.5 MiB. A reader with a line limit must raise it. For example, Go’s bufio.Scanner stops at 64 KiB by default.

Line types#

typeWhat the line holds
headerschema (1), generated_at, max_file_bytes, source (as in the manifest) and product. product is the product as /api/v2/products/ returns it, with its prod_type as a nested object and without findings_count and findings_list.
engagementdata: the engagement as /api/v2/engagements/ returns it. files holds file entries. risk_acceptance holds the ids of every risk acceptance linked to the engagement.
testdata: the test as /api/v2/tests/ returns it. files holds file entries.
findingdata: the finding as /api/v2/findings/ returns it, with the changes below.
risk_acceptancedata: the risk acceptance as /api/v2/risk_acceptance/ returns it, with the changes below.
endcounts: what the stream wrote. See Counts.

Finding lines#

A finding line differs from /api/v2/findings/ in these fields:

  • endpoints is a list of endpoint entries, not ids.
  • files is a list of file entries, not ids.
  • risk_acceptances is a list of risk acceptance ids.
  • request_response_pairs replaces request_response. It holds every request and response pair of the finding, by id, as /api/v2/request_response_pairs/ returns them: id, finding, burpRequestBase64 and burpResponseBase64. The two base64 values are the stored bytes, unchanged.
  • accepted_risks and related_fields are not on the line.

Each endpoint entry has these keys:

KeyLocations offLocations on
idThe endpoint id.The location id.
uriThe endpoint as a URI.The location value.
location_typenullThe location type, for example url.
tagsThe endpoint tags.The location tags.
statusThe endpoint status object, as /api/v2/endpoint_status/ returns it.The location reference object of this finding.

Risk acceptance lines#

A risk acceptance line differs from /api/v2/risk_acceptance/ in these fields:

  • engagement is the id of one engagement that holds the risk acceptance, or null when no engagement holds it. A risk acceptance can be linked to more than one engagement. The engagement lines carry every link in their risk_acceptance ids.
  • notes are nested, not ids.
  • proof replaces path. It holds filename, size, content_type and data_base64, or it is null when there is no proof. The proof follows the same cap and the same missing-file rule as a file entry.

Files#

Engagement, test and finding lines carry their files in files. Each file entry has these keys:

KeyWhat it holds
idThe file id.
titleThe file title.
filenameThe stored file name, with its extension.
sizeThe size in bytes.
content_typeThe content type, from the file name. It is null when the file name has no known extension.
data_base64The file contents in base64.

A file of max_file_bytes or less carries its contents. A larger file keeps its size, and data_base64 is null. The export has no download link for it. To carry larger files, raise max_file_bytes. For example, ?max_file_bytes=52428800 carries files up to 50 MiB. While the server writes a line, its memory use peaks at about 4.7 times the size of the files on that line. A file that is gone from storage has size and data_base64 set to null, and "error": "missing".

Counts#

The manifest gives counts for each product. The stream gives counts on its end line, in this order:

KeyManifestStream (end.counts)
engagementsEngagements in the product.Engagement lines.
testsTests in the product.Test lines.
findingsFindings in the product.Finding lines.
endpointsEndpoints in the product. With Locations on, locations in the product.Endpoint entries on finding lines. One endpoint on three findings counts three times.
notesNotes on engagements, tests, findings and risk acceptances, once per owner. A note on two findings counts twice.The same, on the lines.
filesFile entries on engagements, tests and findings. A risk acceptance proof is not counted.The same, on the lines.
files_over_capFile entries over the cap. A missing file is not counted.The same, on the lines.
risk_acceptancesRisk acceptances that an engagement of the product holds, or that accept a finding of the product.Risk acceptance lines.
finding_groupsFinding groups in the product.Distinct finding groups on finding lines.

What does not cross#

  • A finding group with no findings. Finding groups cross on the finding lines, so an empty group has no line.
  • Endpoints and locations that have no finding. The manifest counts them in endpoints.
  • The product-level status of a location.
  • Endpoint metadata. Product metadata (product_meta on the header) and finding metadata (finding_meta) do cross.
  • JIRA issue keys and JIRA project settings.
  • Product members and product groups.
  • Engagement presets, report types and CI/CD infrastructure. Their ids stay on the engagement line: preset, report_type, cicd_scm_server, cicd_build_server and cicd_orchestration_engine.
  • API scan configurations and the tool configurations they use. The api_scan_configuration id stays on the test line.
  • Contacts, for example an engagement’s requester. The id stays on the engagement line.
  • Test import history, check lists, languages, technologies and benchmarks.
  • Secrets and instance settings: SSO, JIRA and tool credentials, notifications, API keys and passwords.

A duplicate_finding id can point to a finding in another product. That id dangles in the export of this product. An accepted_findings id on a risk acceptance line can point to a finding in another product in the same way.
